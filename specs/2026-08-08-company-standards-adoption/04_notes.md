# 노트 (결정·함정·왜)

> 시간순 로그는 `03_progress.md`. 여기는 누적 참고용 — 다음에 또 헤매지 않도록 "왜 이렇게 했나"와 함정을 적는다.

## 결정

- **회사 코드는 참고 대상이 아니다.** 회사는 Java/Spring, 여기는 Python/FastAPI 라 코딩 규칙은 이식할 수 없다. 가치가 있는 것은 그 위의 **규칙·절차·게이트 층**이고 그 층은 언어와 무관하다. 조사 범위를 처음부터 이 층으로 좁혔다.
- **에이전트 메모리는 회사와 반대로 간다.** esign-service 12장과 team-pulse 는 영속 메모리를 금지하고 규칙을 `AGENTS.md` 한 파일로 모은다. my-ai-server 는 에이전틱 패턴 레퍼런스라 메모리 활용 자체가 시연 대상이다. 1차 조사(2026-07-12) 때 내린 결정이며 이번에도 유지한다.
- **specs 는 4문서를 유지한다.** 회사는 6문서(`01_README`·`02_spec`·`03_findings`·`04_plan`·`05_tasks`·`06_progress`)지만 1인 프로젝트에 findings/tasks 분리는 과하다. 다만 회사의 **작성 규칙**(문서별 독자 구분, 승인 게이트 명시)은 가져온다 — 문서 수와 작성 규칙은 별개다.
- **폴더 이름은 `YYYY-MM-DD-<슬러그>` 를 유지한다.** 회사는 `<기능명>_<YYYY-MM-DD>` 지만 날짜가 앞에 와야 정렬이 시간순이 된다.
- **번호 체계화가 먼저다.** review 스킬이 "AGENTS.md 8장" 식으로 규칙을 인용하는 구조인데, 지금 my-ai-server AGENTS.md 는 평문 헤딩이라 인용할 대상이 없다. 순서를 뒤집으면 스킬이 규칙을 가리키지 못한다.

### team-pulse 개발표준 — 회사와 다르게 가는 두 곳 (2026-08-08 결정)

- **`PUT`/`PATCH` 는 통일하지 않는다.** 회사는 `PATCH` 로 통일한다. 그 규칙의 진짜 목적은 여러 명이 매번 "이건 PUT 이냐 PATCH 냐"를 논쟁하는 비용을 없애는 것이고, 실무에서 전체 필드를 안 보내면서 `PUT` 을 쓰는 일이 흔해 의미가 이미 깨져 있기 때문이다. 이 레포는 1인이고 **레퍼런스**라 의미를 뭉개는 쪽이 손해다. 전체 교체 `PUT` / 부분 수정 `PATCH` / 애매하면 `PATCH` 로 규칙만 명확히 둔다.
- **식별자는 ULID 가 아니라 UUIDv7 을 쓴다.** 얻는 이득(시간순 정렬·인덱스 지역성)은 같은데, UUIDv7 은 RFC 9562 표준 UUID 라 **UUID 를 지원하는 모든 것이 자동으로 지원한다** (Postgres `uuid` 타입, ORM, 검증기). ULID 는 어디서도 1급 시민이 아니라 26자 문자열로 저장하고 커스텀 타입·검증기를 직접 붙여야 한다 — 사용자가 과거에 겪은 불편이 이것이다.
  - 주의: 표준 라이브러리 `uuid.uuid7()` 은 Python 3.14 부터다. 이 프로젝트는 3.12 라 지금 도입하면 `uuid-utils` 같은 패키지가 필요하다.

- **문서 위생은 한 줄만 가져온다.** "살아있는 문서 vs 불변 스냅샷" 구분은 team-pulse 가 회의록·킥오프 기록 같은 **받은 원본**을 쌓는 레포라서 필요한 것이고, 여기엔 해당 사항이 없다. 값어치가 있는 것은 "문서 제목·머리말에 날짜를 적지 마라" 한 줄이다.
- **표준 분리 구조는 가져오지 않는다.** 회사가 전사 표준(team-pulse)과 레포 규칙(AGENTS.md)을 나눈 것은 여러 레포가 같은 표준을 공유하기 때문이다. 여기는 레포 하나에 1인이라 나눌 이유가 없다 — `AGENTS.md`(공통) + 스택별 `AGENTS.md` 현 구조를 유지한다.

### 구현 중 내린 결정

- **결정**: `AGENTS.md` 를 15장 번호 체계로 전면 재편했다.
  - **이유**: `review` 스킬이 위반을 "AGENTS.md 8장" 으로 인용하는 구조다. 가리킬 주소가 없으면 스킬이 성립하지 않으므로 다른 모든 항목의 전제 조건이었다.
  - **대안**: 헤딩 문구로 인용하기 — 헤딩을 고치면 인용이 전부 깨져서 버렸다.
- **결정**: "제목에 날짜 금지" 규칙에 **판단 기준**("그 날짜가 낡느냐")을 넣었다.
  - **이유**: 규칙을 만든 직후 `standards-adoption.md` 의 "1차 조사 (2026-07-12)" 헤딩이 스스로 걸렸다. 조사가 있었던 시점은 낡지 않는 사실인데 예외가 안 적혀 있어, 그대로 두면 review 스킬이 오탐한다.
  - **대안**: 예외를 열거만 하기 — 새 경우마다 목록을 늘려야 해서 기준 + 예시 방식을 택했다.
- **결정**: CI 를 보류에서 빼고 7단계로 실행했다.
  - **이유**: 사용자가 고민 중이라고 한 것은 TDD·커버리지였고 CI 가 아니었다. CI 는 파일 하나로 끝나고, push 하면 검사 없이 배포되는 상태를 유지할 이유가 없다.
  - **대안**: 없음.
- **결정**: 커버리지 게이트는 걸지 않고 CI 에 이유를 주석으로 남겼다.
  - **이유**: 테스트가 2개뿐이라 어떤 기준선도 숫자놀음이다.
  - **대안**: 낮은 기준(50% 등)이라도 걸기 — 지킬 의미가 없는 기준은 규칙을 가볍게 보는 습관만 만든다고 보아 버렸다.

## 함정 (gotcha)

- **규칙을 새로 만들면 그 규칙으로 이 레포를 한 번 훑어야 한다.** 이번에 "제목에 날짜 금지"를 만들자마자 우리 문서 두 곳이 걸렸고, 그중 하나(`docs/infra.md`)는 진짜 위반, 하나(`standards-adoption.md`)는 규칙이 부정확한 경우였다. 규칙만 적고 넘어가면 둘 다 못 잡는다.
- **1차 조사 결과가 이미 `docs/agentic.md` 에 있다.** "회사 표준과의 관계 (member-api·esign-service 조사, 2026-07-12)" 섹션. 모르고 쓰면 같은 내용을 두 곳에 적게 된다. 상세는 `docs/standards-adoption.md` 로 옮기고 `agentic.md` 에는 링크만 남긴다.
- **회사 레포는 계속 움직인다.** 1차 조사(7-12) 시점에 "esign 에도 CI 가 없다"였는데, 8-07 커버리지 게이트·8-08 `ci.yml` 이 생겼다. 조사 결과에는 **언제 기준인지**를 같이 적어야 다음에 다시 볼 때 판단할 수 있다.
- **적용한 것만 적으면 안 된다.** esign 의 `docs/standards-adoption.md` 는 안 한 것과 그 이유까지 적는다. 이유가 없으면 나중에 "이건 왜 안 했지"를 처음부터 다시 조사하게 된다.
- **문서 제목의 날짜는 손으로 고쳐야 해서 실제 수정과 어긋난다.** team-pulse 에 실제 사고가 기록돼 있다 — 문서 셋이 `date: 2026-07-30` 을 달고 있었으나 마지막 수정은 8월 2일이었고, 그 사이 결정들이 빠진 채 문서만 최신처럼 보였다. **어긋난 날짜는 없는 날짜보다 나쁘다.**
  - **이 레포에서도 이미 발생했다**: `docs/infra.md` 의 `## 현재 상태 (2026-06-28)` 섹션 안에 "BE 배포 완료 (2026-07-12)" 가 들어 있다. 제목 날짜가 본문보다 2주 낡았다. 규칙을 가져올 근거가 남의 사례가 아니라 우리 파일에 있다.
- **커버리지 기준을 현재 측정값으로 잡으면 안 된다.** 정상적인 변경에도 빌드가 서고, 그러면 기준을 낮추는 쪽으로 습관이 생긴다. esign 은 측정값(line 88%·branch 75%)보다 낮게(85%·70%) 잡았다. 도입하게 되면 이 방식을 따른다.
